# Установка Heterion Router на macOS

Инструкция для нового пользователя: как поставить приложение, выпустить первый
ключ, подключить провайдера и проверить, что шлюз отвечает.

Коротко: приложение само поднимает шлюз рядом с собой, ключ оператора выпускается
из интерфейса, провайдер добавляется в разделе «Providers». Терминал нужен только
в двух необязательных сценариях — установка шлюза как системной службы и сборка
веб-дашборда.

---

## 1. Требования

| Что | Значение |
|---|---|
| macOS | **11.0 или новее** (`LSMinimumSystemVersion` в `desktop/gpui/packaging/Info.plist`) |
| Место на диске | **около 23 МБ** на приложение + данные (БД и логи растут со временем) |
| Архитектура | собирается под Apple Silicon (arm64); проверялось на macOS 27.2 |
| Xcode | **не нужен**, если берёте готовый бандл; нужен только при сборке из исходников |
| Rust | не нужен; нужен только при сборке из исходников (toolchain `1.99.0`, закреплён в `rust-toolchain.toml`) |

Размер 23 МБ — измеренный размер собранного бандла
`desktop/gpui/dist/Heterion Router.app`: оболочка 13.3 МБ + sidecar-шлюз 9.5 МБ +
иконки. Данные пользователя лежат отдельно, в `~/.heterion-router` (см. §3).

---

## 2. Вариант A: готовый бандл (рекомендуемый)

### 2.1. Распаковка и перенос

1. Скачайте ZIP-архив и распакуйте его двойным кликом (архив из macOS Finder
   распаковывается без сторонних программ).
2. В распакованной папке лежит `Heterion Router.app` — перетащите его в
   `/Applications` (Finder → «Программы»).

### 2.2. macOS заблокирует приложение (Gatekeeper)

Бандл подписан **ad-hoc** (`codesign --force --deep --sign -`) и **не нотаризован** —
это осознанная позиция сборки (`desktop/scripts/build-app.sh`). Поэтому при первом
запуске macOS покажет «Heterion Router» повреждённым или неподписанным. Есть два
способа это обойти.

**Способ 1 — через контекстное меню (без терминала).**

1. Найдите `Heterion Router.app` в `/Applications`.
2. Нажмите на него **правой кнопкой** → «Открыть».
3. В диалоге подтверждения нажмите «Открыть» ещё раз.

После этого macOS запомнит приложение и больше не спросит.

**Способ 2 — снять карантин из терминала.**

```sh
xattr -cr "/Applications/Heterion Router.app"
```

`xattr -cr` снимает с каталога и всех файлов внутри него метку карантина
(`com.apple.quarantine`), после чего приложение запускается обычным двойным
кликом. Команду нужно выполнять от имени пользователя, который будет запускать
приложение; `sudo` не требуется.

> Запуск из терминала (`open "/Applications/Heterion Router.app"`) — третий вариант,
> но он не снимает карантин: приложение всё равно спросит подтверждение.

### 2.3. Вариант B: сборка из исходников

Если готового бандла нет, нужен **Xcode** (gpui компилирует Metal-шейдеры через
`xcrun metal` на этапе сборки) и Rust 1.99:

```sh
git clone https://github.com/Egorich-print/heterion-router.git
cd heterion-router
desktop/scripts/build-app.sh
```

Скрипт соберёт и оболочку, и sidecar-шлюз и сложит бандл в
`desktop/gpui/dist/Heterion Router.app`; запустить — `open` из этого каталога.
Сборка холодная — около двух минут.

---

## 3. Первый запуск

1. Запустите **Heterion Router** из `/Applications`.
2. Приложение **само поднимает шлюз**: бинарь `heterion-router-gateway` лежит
   рядом с исполняемым файлом приложения (`Contents/MacOS/`), и оболочка
   запускает его как sidecar на порту **20129**. Шлюз работает, пока открыто
   приложение; при закрытии приложения шлюз останавливается.
3. Каталог данных — **`~/.heterion-router`** (legacy-каталог `~/.omniroute`
   используется, если нового нет). Каталог переопределяется переменной
   `HETERION_ROUTER_DATA_DIR`.
4. На экране входа нажмите **«Create first key»**. На свежей установке в базе
   ещё нет ни одного ключа, поэтому аутентификация ещё открыта — ключ выпускается
   прямо из приложения, без правки БД вручную.

   > Интерфейс приложения — английский: подписи на кнопках приведены как в
   > реальном приложении («Create first key», «Add provider», «Issue key»),
   > инструкции в этом документе — по-русски.

Ключ оператора сохраняется в `<каталог данных>/desktop/operator-key.json`
(файл `0600`, каталог `0700`) и используется и для входа в приложение, и для
запросов к `/v1/*`. Сам секрет шлюз показывает ровно один раз — сразу после
выпуска; в базе лежит только хеш.

> Если в вашей сборке кнопки «Create first key» нет, выпустите ключ вручную
> (на свежей базе bearer не требуется — аутентификация ещё открыта):
>
> ```sh
> curl -s -X POST http://127.0.0.1:20129/api/keys \
>   -H "Content-Type: application/json" \
>   -d '{"name":"operator"}'
> ```
>
> В ответе будет поле `key` — его и нужно вставить на экране входа.

## 4. Провайдеры (раздел «Providers»)

Раздел **«Providers»** → **«Add provider»** → найдите провайдера в поле
**«Search providers»** (поиск идёт по названию и по id) → выберите его из
каталога → вставьте **свой API-ключ провайдера** → **«Save»**.

Ключ провайдера шифруется и кладётся в базу шлюза (префикс `enc:v1:`); в открытом
виде он больше нигде не показывается — только префикс. Если провайдер работает
без ключа (keyless), поле ключа можно оставить пустым.

Подробности по конкретным провайдерам, их авторизации и моделям — в
[docs/PROVIDERS.md](PROVIDERS.md).

## 5. Проверка, что всё работает

### 5.1. Шлюз жив

```sh
curl -s http://127.0.0.1:20129/healthz
```

Ожидаемый ответ (порядок полей не важен):

```json
{"status":"ok","backend":"routing","started_unix":1762810000}
```

`backend` — имя активного бэкенда (`routing` — штатный режим). `/healthz`
**всегда публичен**, даже когда аутентификация включена, поэтому по нему удобно
проверять, что процесс жив, не имея ключа.

### 5.2. Список моделей

```sh
curl -s http://127.0.0.1:20129/v1/models \
  -H "Authorization: Bearer sk-ваш-ключ"
```

Здесь видно, какие модели (или комбо) доступны для роутинга. Этот же список
показывает раздел «Overview» в приложении.

### 5.3. Запрос к модели

```sh
curl -s http://127.0.0.1:20129/v1/chat/completions \
  -H "Authorization: Bearer sk-ваш-ключ" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "имя-комбо-или-модели",
    "messages": [{"role": "user", "content": "Привет"}]
  }'
```

`sk-ваш-ключ` — **плейсхолдер**: подставьте ключ, выпущенный в приложении.
`имя-комбо-или-модели` — строка из §5.2.

## 6. Конфликты портов

На этой машине одновременно могут жить три вещи:

| Кто | Порт | Чем переопределяется |
|---|---|---|
| Установленная служба `com.heterion.router` | `20128` | `HETERION_ROUTER_PORT` / `OMNIROUTE_RUST_PORT` (в plist службы) |
| Sidecar-шлюз внутри приложения | `20129` | `HETERION_ROUTER_SIDECAR_PORT` / `OMNIROUTE_SIDECAR_PORT` |
| Блокировка второго экземпляра приложения | `20130` | `HETERION_ROUTER_INSTANCE_LOCK_PORT` |

Порт, на котором шлюз слушает сеть, задаётся `HETERION_ROUTER_PORT`
(legacy-имя `OMNIROUTE_RUST_PORT`), адрес — `HETERION_ROUTER_HOST` (по умолчанию
`127.0.0.1`, то есть только loopback).

**Если служба на 20128 уже крутится** — приложению это не мешает: оболочка всегда
передаёт sidecar-шлюзу **явный** порт, поэтому он не наследует
`HETERION_ROUTER_PORT=20128` из окружения и не упирается в занятый порт. Живой
sidecar занимает 20129.

**Если 20129 занят чем-то ещё** (например, локально поднятым шлюзом в
debug-режиме), запустите приложение с другим портом:

```sh
HETERION_ROUTER_SIDECAR_PORT=20131 open "/Applications/Heterion Router.app"
```

Порт должен быть свободен — иначе шлюз не поднимется, и в логе приложения
появится предупреждение `could not start the bundled gateway`. Номер порта
(instance lock) при этом остаётся 20130: если приложение уже открыто, второе
запущенное молча завершится.

**Отдельно про debug-сборку оболочки**: в debug-режиме sidecar не поднимается, и
оболочка говорит с уже запущенным шлюзом — тогда порт берётся из
`HETERION_ROUTER_PORT` / `OMNIROUTE_RUST_PORT` (то есть тот же, что и у службы).

## 7. Установка шлюза как macOS-службы (launchd)

Нужно, если шлюз должен жить без открытого приложения и отдавать API другим
машинам в сети. Скрипт живёт в репозитории: `scripts/deploy-service.sh`.

### 7.1. Что делает скрипт

1. `cargo build --release` — собирает бинарь шлюза.
2. Копирует его в `~/.local/bin/heterion-router-gateway` (путь переопределяется
   `HETERION_SERVICE_BIN`), подписывает ad-hoc и подменяет файл через временное
   имя, чтобы не заменить бинарь «на лету» у работающего процесса.
3. Если plist уже существует — обновляет в нём путь к бинарю и сохраняет бэкап.
4. Перерегистрирует job: `launchctl bootout gui/$(id -u)/com.heterion.router`,
   затем `launchctl bootstrap gui/$(id -u) <plist>`. **Одного `kickstart`
   мало**: launchd кэширует определение job, поэтому после замены бинаря job
   надо перерегистрировать.
5. Ждёт до 30 секунд ответа на `http://127.0.0.1:20128/healthz`.

Служба запускается **не** из `target/release` на внешнем томе, а из копии на
системном диске: macOS для свежезаписанного бинаря на смонтированном томе
гоняет проверку подписи (`trustd`), и она может зависнуть — процесс висит в
`dyld` и не слушает порт. Копия на системном диске стартует всегда и переживает
отмонтирование тома.

### 7.2. plist

Plist **машинно-локальный** и в репозитории не хранится — у каждой машины свой
(путь к бинарю и каталог данных разные). Файл лежит в
`~/Library/LaunchAgents/com.heterion.router.plist`. Шаблон:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
	<key>EnvironmentVariables</key>
	<dict>
		<key>HETERION_ROUTER_PORT</key>
		<string>20128</string>
		<key>HETERION_ROUTER_HOST</key>
		<string>127.0.0.1</string>
		<key>HETERION_ROUTER_DATA_DIR</key>
		<string>HOME/.heterion-router</string>
		<key>RUST_LOG</key>
		<string>info</string>
	</dict>
	<key>KeepAlive</key>
	<true/>
	<key>Label</key>
	<string>com.heterion.router</string>
	<key>ProgramArguments</key>
	<array>
		<string>HOME/.local/bin/heterion-router-gateway</string>
	</array>
	<key>RunAtLoad</key>
	<true/>
	<key>StandardErrorPath</key>
	<string>HOME/Library/Logs/heterion-router.err.log</string>
	<key>StandardOutPath</key>
	<string>HOME/Library/Logs/heterion-router.out.log</string>
	<key>ThrottleInterval</key>
	<integer>10</integer>
</dict>
</plist>
```

Замените `HOME` на свой домашний каталог. `HETERION_ROUTER_HOST`:
`127.0.0.1` — только локально; `0.0.0.0` — доступ из сети, но тогда в базе
**обязан быть хотя бы один ключ**, иначе шлюз не стартует (не-loopback bind без
аутентификации блокируется).

### 7.3. Запуск и проверка

```sh
scripts/deploy-service.sh                       # сборка + установка + перезапуск
launchctl kickstart -k gui/$(id -u)/com.heterion.router   # если job уже установлен
curl -s http://127.0.0.1:20128/healthz          # проверка
```

Возможности и ограничения (из кода, а не из догадок):

- перезапуск из интерфейса приложения (раздел «Overview» / кнопка «Restart now»)
  работает **только** под супервизором (`launchd`); если служба запущена руками,
  шлюз вернёт `409`;
- после замены бинаря `kickstart` не подхватывает новый файл — нужен
  `bootout` + `bootstrap`, как это делает `scripts/deploy-service.sh`.

## 8. Веб-дашборд (Svelte)

Приложение на GPUI — нативная оболочка поверх admin-API. Параллельно существует
веб-дашборд (Svelte), который шлюз раздаёт сам: удобно, когда нужно открыть его
из другой машины или из браузера.

Сборка:

```sh
npm --prefix desktop/ui ci
npm --prefix desktop/ui run build
```

Собранный бандл лежит в `desktop/ui/dist`. После сборки шлюз отдаёт его на
**http://127.0.0.1:20128/** (или на порту службы, см. §7).

Если сборка лежит **не в дереве исходников**, укажите каталог сборки через
`HETERION_ROUTER_UI_DIR` (legacy: `OMNIROUTE_UI_DIR`) — например, в plist
службы:

```xml
<key>HETERION_ROUTER_UI_DIR</key>
<string>/путь/к/desktop/ui/dist</string>
```

Без этой переменной и без каталога `desktop/ui/dist` рядом с исходниками шлюз
остаётся «только API»: на `/` он отвечает текстом
`dashboard not built: run npm install && npm run build in desktop/ui, or set
HETERION_ROUTER_UI_DIR`.

Веб-дашборд, как и приложение, просит API-ключ оператора на экране входа (в
браузере он хранится в `localStorage` — это свойство веб-фронтенда; в нативном
приложении ключ лежит в файле с правами `0600`).

Для разработки: `npm --prefix desktop/ui run dev` поднимает Vite; прокси по
умолчанию ходит на `20128`, поэтому для dev-шлюза на `20129` нужен
`VITE_GATEWAY_URL=http://127.0.0.1:20129`.

## 9. Диагностика

### 9.1. Где лежат логи

| Что | Путь |
|---|---|
| Лог шлюза | `<каталог данных>/gateway.log` (ротация по дням: `gateway.log.2026-11-11`) |
| stdout/stderr службы | `~/Library/Logs/heterion-router.out.log` / `.err.log` (если так настроен plist) |
| База | `<каталог данных>/storage.sqlite` |
| Ключ оператора | `<каталог данных>/desktop/operator-key.json` (`0600`) |
| Логи приложения (GPUI) | раздел **«Logs»** в самом приложении |

Последние строки лога шлюза можно посмотреть и из приложения: раздел «Logs»
показывает и хвост `gateway.log`, и последние вызовы (`/api/logs/app`,
`/api/logs`).

### 9.2. Типовые сообщения шлюза

| Сообщение | Что значит |
|---|---|
| `heterion-router-gateway listening on http://127.0.0.1:20129` | шлюз поднялся и слушает порт |
| `completion model=… stream=false` | запрос к модели отработал |
| `completion failed model=…: …` | запрос упал; чаще всего внутри `upstream status <код>: …` |
| `upstream status 401: …` | провайдер не принял ключ — проверьте ключ провайдера и активность подключения |
| `upstream status 429: …` | лимит запросов у провайдера |
| `upstream status 5xx: …` | падение апстрима; шлюз обычно переключается на следующего кандидата |
| `WARN repetition guard model=… source=content\|reasoning ratio=… repeats=… words=… — answer truncated` | ответ модели обрезан роутером (вырожденное повторение); клиент получит `finish_reason: "length"` |
| `api key last_used_at update failed: …` | база занята или недоступна; на работу не влияет |
| `could not start the bundled gateway` | в логе приложения: sidecar не поднялся (занят порт или бинарь рядом с оболочкой отсутствует) |

### 9.3. Частые проблемы

| Симптом | Что делать |
|---|---|
| macOS: «Heterion Router» повреждён | §2.2: правой кнопкой → «Открыть» или `xattr -cr` |
| Приложение открылось, но шлюз не отвечает на `/healthz` | проверьте порт (§6), свободен ли 20129; смотрите лог приложения |
| `401` на `/v1/*` | вставьте настоящий ключ оператора; на свежей установке вставьте ключ, выпущенный в приложении |
| `404` на модели | проверьте `/v1/models` — имена моделей/комбо задаёт оператор |
| Порт 20128 не отвечает после установки службы | смотрите `~/Library/Logs/heterion-router.err.log` и `launchctl list \| grep heterion` |
| Веб-дашборд открывается, но пустой | пересоберите `desktop/ui` или задайте `HETERION_ROUTER_UI_DIR` (§8) |

### 9.4. Где смотреть ключи и подключения

- **В приложении:** раздел **«Keys»** → **«Issue key»** — выпуск ключа оператора
  (видны только префиксы; полный секрет показывается один раз сразу после
  выпуска), кнопка отзыва ключа действует немедленно. Раздел **«Providers»** →
  **«Add provider»** — подключения провайдеров, их активность и приоритет.
- **В базе:** таблица `api_keys` (в столбце `key` лежит маркер `hash-only:<id>`,
  а не сам секрет) и таблица подключений провайдеров; зашифрованные секреты
  провайдеров лежат с префиксом `enc:v1:`.
- **Не выводите и не пересылайте** содержимое `operator-key.json` — это
  действующий bearer оператора.
